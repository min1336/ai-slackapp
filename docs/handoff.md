# 결항확인서 AI 분석 기능 Handoff

## 현재 구현 상태

### 플로우 요약
```
JotForm 설문 제출
  → Google Sheets (결항데이터 탭) 기록
  → 봇 폴링 (CancellationImageService.poll_and_upload)
    → Slack 카모아_알림_결항확인서 채널에서 예약번호로 스레드 탐색
    → Google Drive에서 폴더(고객명_예약번호) 찾기
    → 이미지/PDF 다운로드 → Slack 스레드에 업로드
    → Gemini 분석 → ✔/✘ 이모지 + 검증 결과 댓글
    → 운영현황(결항관리) 시트에 결과 기록
```

## 결항확인서 이미지 패턴 분석

실제 prod 데이터 분석 결과 (2025-12 ~ 2026-03 접수분 7건 Gemini 분석 완료).

### 문서 유형 1 — 항공사 운항정보확인서

대상: 진에어, 대한항공, 이스타항공 등

| 필드 | 추출 가능 여부 | 비고 |
|------|--------------|------|
| 항공편 번호 | ✅ 항상 | LJ473, KE1627 형태 |
| 결항 날짜 | ✅ 항상 | |
| 결항 사유 | ✅ 항상 | 기상, 기체결함 등 |
| 발급 기관 | ✅ 항상 | |
| 고객명 | ⚠️ 없는 경우 많음 | 진에어 운항정보확인서는 미기재 |
| 예약번호 | ❌ 거의 없음 | 항공사 내부 코드(DU2Y2B 등)만 존재 |

**주의:** 진에어 운항정보확인서는 고객명/예약번호가 없는 것이 정상. 예약번호 불일치를 부적합으로 판정하면 오탐 발생.

### 문서 유형 2 — 해운사 결항확인서

대상: 대아고속해운 등

| 필드 | 추출 가능 여부 | 비고 |
|------|--------------|------|
| 고객명 | ✅ 있음 | 동반 탑승객 포함 |
| 출발일/항로 | ✅ 있음 | |

| 발급 기관 | ✅ 있음 | |
| 예약번호 | ⚠️ 있는 경우 있음 | |

## 댓글로 제공 가능한 정보

### 현재 제공 중
- `✔/✘` 이모지 (적합/부적합)
- 검증 결과 Block Kit 메시지 (is_valid, confidence, 판단근거)
- 운영현황 시트에 `검증결과` / `검증사유` 기록

### 추가 가능한 것들

**1. 결항 날짜 추출 → 환불 기준일 자동 표시**
```
결항일: 2025-12-13
환불 신청 가능 기간: ~2026-01-13 (결항일 기준 30일)
```

**2. 항공편 번호 기반 중복 감지**
- 동일 항공편(LJ473 등)으로 여러 건 접수 시 운영자에게 알림
- "동일 편명 접수 N건" 표시

**3. 불일치 항목 명시**
```
⚠️ 확인 필요
- 예약번호: 접수 RS1938611 / 문서 미기재
- 고객명: 문서에 없음
```

**4. 문서 유형 자동 분류**
- 항공/해운 구분 → 담당 팀 라우팅 자동화 가능

**5. 이미지 품질 불량 감지 → 재제출 요청**
```
📷 이미지 품질 불량 (흐림/잘림)
→ 선명한 이미지로 재제출 요청 필요
```

## 알려진 이슈 및 제한사항

### Gemini API
- **무료 티어 한도: 20회/일** — prod에서 하루 접수가 20건 초과 시 분석 실패
- 유료 API 키 사용 시 해결 (현재 `.env`의 `GEMINI_API_KEY` 교체 필요)
- 타임아웃 60초 설정, 이미지 10장 초과 시 자동 제한

### Slack 채널 접근
- 봇이 채널 멤버가 아니어도 `chat:write.public`으로 업로드 가능
- 단, 채널 히스토리 읽기는 `channels:join` 스코프 없어서 불가
- 채널 초대(`/invite @cancellation-bot-test`)하면 히스토리 읽기 가능해짐

### 예약번호 불일치 오탐
- 항공사 운항정보확인서는 예약번호 미기재가 정상
- 현재 프롬프트가 예약번호 없으면 불일치로 판단 → `is_valid=false` 오탐
- 개선 방향: 문서 유형별 검증 기준 분리 필요
